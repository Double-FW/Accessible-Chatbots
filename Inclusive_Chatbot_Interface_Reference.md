# Inclusive chatbot interfaces reference

Version 1.1 · 24 September 2026 · Intended for retrieval during interface design, implementation and testing

## Purpose and use

This reference defines testable behaviour for a chatbot embedded in a web page or opened in a modal dialog. Retrieve the relevant sections when generating design specifications, code, acceptance criteria or test plans. Apply the host organisation's approved design system and current component documentation, then test the resulting integration in its actual page. The notes in *ChatBot Documentation Outline* inform the scope. Source links at the end distinguish standards, informative implementation guidance and product documentation.

**Platform rule.** The requirements for discovery, focus, transcript navigation, announcements, recovery and testing apply to any chatbot implementation. Microsoft Copilot Studio, Bot Framework Web Chat and Adaptive Cards appear only as examples from the source outline. Apply their product-specific instructions only when that product and feature are present in the chosen stack. For another vendor or a bespoke chatbot, inspect its actual components and version, map the same user outcomes to that implementation, and document and test its behaviour. Do not copy Microsoft's keyboard shortcuts, live-region architecture, terminology or integration APIs into a different implementation by default.

**Scope boundary.** The source outline marked the accessibility of generated rich content, media and attachments out of scope for its original project. This reference specifies the interface and the behaviour of generated messages, links, controls and errors. If the generated content includes documents, images, charts, code, cards or media, evaluate their accessibility under a separately documented content policy; the interface must not expose unusable generated controls or unsafe markup.

## Interpretation and priority

- Target WCAG 2.2 A and AA for the chatbot and its integration into the host page. Record actual criterion applicability and test evidence. WCAG is a minimum conformance target, not a complete inclusive design specification. Separate conformance obligations from design system rules and additional recommendations. Do not present AAA criteria as AA requirements.
- The original outline named WCAG 2.1 AA. WCAG 2.2 A/AA is the current recommended project baseline here and includes relevant additions such as focus not obscured, target size minimum and accessible authentication. If a contract fixes WCAG 2.1, document the contractual target and assess 2.2 separately.
- The outline's suggested 44 × 44 CSS pixel targets, 45–90 character line lengths, Grade 8 reading level and response acknowledgement under two seconds are **design targets to validate**, not universal WCAG 2.2 AA thresholds. WCAG 2.2 SC 2.5.8 generally sets 24 × 24 CSS pixels with exceptions; 44 × 44 is a useful larger target. Focus Appearance SC 2.4.13 is AAA; a visible focus indicator, unobscured focus and relevant non-text contrast remain important at A/AA.
- WAI-ARIA patterns and WCAG techniques are informative implementation resources. Choose the actual DOM and interaction pattern on its merits; a `role` alone never implements keyboard behaviour. Inspect the versions and customisations of whichever chat SDK and component library the project uses before asserting that their defaults meet a requirement.

## Interface architecture and discovery

**Presence on the page.** Make the entry point discoverable in visual layout, DOM reading order and keyboard order, with a persistent meaningful name such as “Open support chat”. Explain its purpose and AI identity or limits near the entry point or at the start of the chat. Do not steal focus on page load, start speech automatically, or insert a surprise live announcement just because the page contains a chatbot. If an invitation appears dynamically, it must be dismissible, visually perceivable and announced once at appropriate politeness when genuinely relevant; it cannot obstruct the task or reappear repeatedly after dismissal. Offer a non-chat support route when one exists.

**Embedded region.** Give the expanded chat a visible heading and an accessible region name if a region meaningfully improves landmark navigation. Place it predictably in reading order. The launcher communicates expanded state and relationship to the panel (`aria-expanded`, and `aria-controls` if useful and reliable). A labelled “Close chat” or “Collapse chat” button is distinct from “End conversation” and “New conversation”. Keyboard users can Tab from the chat back into the host page in a logical sequence. Do not mark the host page inert or declare an embedded panel modal. On deliberate opening, choose initial focus after testing: retain focus on the toggle or move to a useful heading or composer if this helps and is predictable. On collapse, if focus is inside the hidden panel, return it to the launcher or nearest stable equivalent.

**Modal region.** Use the native `<dialog>` opened with `showModal()` where supported and compatible with the application; otherwise implement the complete modal dialog pattern. Provide an accessible name from a visible title; provide a concise description only when useful. On open, move focus inside to a purposeful element, often a static heading or the composer depending on content length and task. Make the outside page inert for pointer and keyboard interaction, constrain Tab and Shift+Tab inside, provide a visible close control, support Escape unless closing would itself create a serious data loss condition requiring confirmation, and restore focus to the invoker or a logical successor. Only set `aria-modal="true"` when the entire interface really behaves as modal. If an embedded iframe hosts the chat, manage the outer dialog and its focus boundary in the parent page and test the focus path across iframe boundaries. On small screens, ensure the virtual keyboard, zoom, reflow and browser viewport do not hide the composer or close control. A non-modal floating panel follows the embedded rule, not the modal rule.

**Shared presentation.** Use existing accessible buttons, text fields, links, cards, indicators and dialog components where they satisfy these behaviours. Verify contrast for text, component boundaries and meaningful icons; visible and unobscured focus; text resize and reflow; text spacing; orientation; reduced motion; pointer targets; and forced colours. Place help consistently. Use clear control labels that distinguish action from outcome. All author-created shortcuts must be discoverable, avoid conflicts and meet SC 2.1.4 where single-character shortcuts apply.

## Focus and transcript navigation

- Focus moves because of a clear user action or a necessary recovery step, never because a new answer arrives. Keep focus in the composer after Send unless there is a documented reason to move it. An error should identify the issue and put focus where it helps correction; announce the error without unnecessarily sending the user to the top of a long transcript.
- Transcript review is independent from focus management. Give users an efficient way to reach the chat history, navigate messages, reach new messages and return to the composer. Do not force Tab through every historical action. Preserve reading and scroll positions when new content arrives; if the user is reviewing older turns, offer a labelled “New messages” or “Go to latest message” action.
- If using Microsoft Bot Framework Web Chat, inspect its current documented composite transcript navigation and preserve the working Up, Down, Home, End, Enter and Escape behaviour as applicable. Its internal focus handling when entering an interactive card is distinct from a trap around the entire embedded chat. With another SDK, preserve its tested accessible navigation or design and test an appropriate pattern for the selected implementation; do not impose Web Chat's shortcuts on it. Document any deliberate override and rerun keyboard and assistive technology tests.
- Each message needs a stable identity and discernible sender, message content and relevant state; avoid repetitive decorative text. Group long histories into navigable sections where useful. Virtualisation must not silently remove the message a user is reviewing or break screen reader navigation. Keep link and action labels understandable when encountered out of context.

## Notifications and generated messages

Design one **announcement ownership map** for the entire integration: the host page, vendor chat widget and any custom announcement service must agree which one announces each event. Determine what the actual integrated widget already announces by testing. Never add a second live region around a vendor transcript merely because the page also needs status messages.

| Event | Visible communication | Programmatic behaviour | Focus behaviour |
| --- | --- | --- | --- |
| Chat becomes available on page | Named launcher, purpose and optional invitation | No automatic speech for a static launcher; a truly dynamic invitation may use one polite status | Stay where user is |
| Panel opens | Heading and controls | Dialog name is available on entry; avoid a separate duplicate “Chat opened” alert | Embedded: documented choice; modal: move inside |
| User sends message | Message appears with pending or sent state | Usually avoid echoing the entire user's input; announce failure or materially changed delivery state | Usually remain in composer |
| Generation starts or upload proceeds | Persistent “Generating” or progress display | One concise polite status; updates only at meaningful intervals | No movement |
| New response completes | New message, sender and accessible structure | Announce once using the vendor mechanism or an intentionally designed log/live region; offer navigation if long | No movement |
| User reads older turns while responses arrive | Count or “New messages” control | Polite notification without forced reading of all unseen content | Preserve position |
| Recoverable error or connection loss | Clear explanation, retry and alternate route | Polite status or contextual error association; urgent alert only if immediate action is essential | Move only when useful for recovery |
| Session warning | Remaining time, effect on draft/history, extend action | Timely status, not an ephemeral toast | Keep accessible action reachable |

For a bespoke chat, `role="log"` with an accessible name is one W3C-documented way to expose sequential message updates; its implicit politeness can announce newly appended entries. Another architecture uses a navigable transcript plus a separate controlled live region. Do not use both to announce the same content. A generic `aria-live="polite"` on the entire growing transcript can cause repeated or excessive speech. Keep live content short and atomic when possible. Use `role="status"` for ordinary progress and reserve `role="alert"` or an alert dialog for situations that genuinely require interruption. Test with real browser and screen reader combinations: live region timing varies.

For streamed responses, do not announce each token or reinsert a changing message in a way that causes repeated speech. Distinguish “Generating response”, content available, and “Response complete”. Choose whole-message announcements, manageable chunks or a short completion notice with a direct way to read the answer based on user testing. If interruptible, label “Stop generating”; preserve and identify partial text, retry and regenerate paths. Avoid automatic focus and forced scrolling; respect reduced motion. Announcements of the answer should not erase a user’s place while reading earlier messages.

## Input, cognition and recovery

Label the composer and explain submission, attachments, limits and any privacy implications before use. Preserve multiline editing conventions; make Enter-to-send behaviour clear and provide a Send button. Suggested prompts are real buttons with meaningful names; selection does not unexpectedly send unless stated. Group related controls in cards with appropriate labels and keyboard order. Explain AI identity, uncertainty, citations where supplied, memory and limitations in plain language. Give a path to correct prior information, change direction, request a shorter or simpler answer and access human support if offered. Review significant details before consequential actions and confirm outcomes. Do not impose a universal reading grade as a substitute for testing comprehension with intended users.

Avoid unnecessary time limits. If a time limit applies, select and implement a permitted route under SC 2.2.1, including any applicable exception; for the “Extend” route the warning provides at least 20 seconds and allows extension at least ten times. Preserve drafts and task state where permitted, explain what expiry loses, and recover to a comprehensible screen. Errors identify what happened and a practical next step without discarding user input. Authentication and upload flows need specific failure recovery.

## Evidence and testing model

Create atomic requirements with stable IDs and fields: behaviour, trigger, expected outcome, presentation variant, applicable WCAG 2.2 A/AA SC, design rule or recommendation, implementation owner, test method, evidence, status and exception. Test the **integrated host page** and chat in closed, open, loading, successful, failure, reconnection and expiry states; include mobile, desktop and long-history states.

- **Automatable checks:** axe-core scans across states for detectable issues such as names, label associations, invalid ARIA, some contrast, language and structural errors; browser integration assertions for launcher state, dialog name and modal inertness, focus entry and restoration, keyboard exits, status ownership, duplicate announcement nodes, no focus change on incoming messages, draft persistence and reduced-motion styling. Tests of DOM state and keyboard focus are deterministic checks, but do not establish screen reader experience. Record tool version and unsupported or incomplete results.
- **Manual expert checks:** keyboard-only and switch-like sequences; screen readers across agreed browser/AT combinations; exact spoken output and announcement timing; long history navigation; visual reading order, focus, zoom/reflow, forced colours, text spacing, contrast exceptions and responsive virtual keyboard; no unsolicited speech, focus or scrolling; timers, cards, attachments, failure and retry. Record steps, expected and observed outcomes, screenshots or logs when useful.
- **User testing:** recruit people who use screen readers, magnification, keyboard or alternative input, and people with cognitive, literacy or anxiety-related needs relevant to the product. Include sighted and vision-impaired participants. Test discoverability, orientation, trust, comprehension, recovery and task completion with both modal and embedded variants when both ship. Consent-based analytics can show completion, abandonment, repeated attempts and help requests, but must not infer disability from input behaviour or expose conversation contents unnecessarily.

Track coverage separately from test pass rates. A clean axe scan is not an accessibility sign-off. Run representative tests when design tokens, framework, chat SDK, model response format or host page changes. Record ownership, exceptions, affected users, remediation and follow-up. All experimental variants must meet the same baseline. AI may propose fixes and prioritise signals, but consequential changes and claims of conformance need accountable human review and user evidence.

## Source register

- [WCAG 2.2 normative standard](https://www.w3.org/TR/WCAG22/) and [Quick Reference](https://www.w3.org/WAI/WCAG22/quickref/): A/AA criteria and timing, target size and focus provisions.
- [WAI-ARIA APG modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) and [W3C native dialog technique H102](https://www.w3.org/WAI/WCAG22/Techniques/html/H102): modal keyboard, focus and inert behaviour. Informative guidance and example.
- [W3C ARIA23 chat log technique](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA23.html) and [Understanding status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html): notification semantics. Informative guidance.
- [Microsoft Bot Framework Web Chat accessibility documentation](https://github.com/microsoft/BotFramework-WebChat/blob/main/docs/ACCESSIBILITY.md), [project repository](https://github.com/microsoft/BotFramework-WebChat) and [Copilot Studio documentation](https://learn.microsoft.com/en-us/microsoft-copilot-studio/): vendor behaviours and integration. Check the installed version.
- [axe-core repository](https://github.com/dequelabs/axe-core): automated engine and its coverage limitations.
